尺寸张量准备三轮只实际消耗约1.9–2.5ms线程CPU，却有10.5–45.3ms墙钟时间；图提交也有类似差异。这支持进一步检查主线程调度、Python/GIL交接、小张量创建和同步，尚不能仅凭这些范围把每段停顿唯一归因到GIL。各轮非自愿上下文切换165–295次，调度波动值得关注。

三个计时区间读取约58.4MB逻辑输入、14559次read类调用，`read_bytes`增量均为0：这组是热页缓存测量，物理磁盘读取不能解释当前主要CPU开销。JSON编码约11–12ms累计CPU，最后等待JSON Future小于0.05ms；大部分编码已在流水线上重叠。

剩余退出区间包括诊断输出、worker最后日志刷新、解释器调用退出和OS/CUDA资源回收，不能全部归因某一个系统调用。已有THP设置仍保留，不做系统级修改。

## GPU时间线与低开销交叉验证

节点无nsys，使用PyTorch CPU/CUDA profiler单独采集一次。记录25次CUDA Graph replay、19050个kernel，其中13731个短于5微秒。GPU kernel/copy/memset活动区间并集128.891ms，首尾GPU活动跨度258.413ms，间隙129.522ms。profiler会扰动CPU调度，不能把这个间隙直接当作正常运行的GPU空闲量；含导出trace的1.927秒总时间没有性能排名意义。

因此另做三轮仅CUDA Event标记graph、图像H2D及检测D2H包络的诊断：

| 指标（ms） | 第1轮 | 第2轮 | 第3轮 |
| --- | ---: | ---: | ---: |
| 核心处理 | 241.291 | 231.451 | 186.414 |
| graph/copy包络并集 | 149.674 | 150.880 | 133.623 |
| 首尾包络跨度 | 211.046 | 199.524 | 161.907 |
| 包络之间的空档 | 61.372 | 48.644 | 28.284 |
| 核心后至进程结束的剩余区间 | 72.248 | 73.394 | 68.359 |

图包络含图内的小间隙，少量尺寸传输未独立标记，这不是精确kernel利用率。不过低开销测量也保留28–61ms批次间空档，支持CPU供给/调度仍值得优先检查。第三轮更快同时说明节点有波动，不能挑最快一轮作为正式成绩。

profiler中图像H2D累计9.661ms，特征pack累计7.801ms，ReLU-affine累计4.555ms；大量转换、逐元素操作和小GEMM也分散占时。后续GPU优化可检查特征布局/转换和小算子融合，但当前没有单一大kernel独占整体时间的证据。H2D与计算及其他流存在重叠，不能简单相加。

## 后续顺序与复现

1. 固定8核，优先验证解码线程与主线程争用，检查输入槽复用和尺寸张量准备的短暂停顿；必须在全本地日志条件下做交替对照，不能继承先前共享日志下的workers6/8筛查结论。
2. 单独定位约63–73ms退出区间的主机内存与CUDA资源回收成分；保留正常退出计时边界和现有THP开关。
3. 再检查GPU特征pack、dtype/layout转换和大量短kernel。既往在其他环境失败的方案不能仅凭本次粗粒度数据直接晋级。
